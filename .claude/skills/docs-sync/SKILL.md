# docs-sync — 제품 공식 문서 전수조사 & 동기화

이 저장소(docs-zip)의 각 최상위 디렉터리는 하나의 제품/프로젝트(예: `claude-code/`, `codex/`, `openrouter/`)의 공식 문서·개발자 문서를 전수조사해 한국어 마크다운으로 정리한 문서 세트다. 이 스킬은 사용자가 지정한 디렉터리를 그 제품의 **현재 최신 공식 문서**와 일치하도록 동기화한다.

최종 결과물:

- 기존 문서의 사실 오류·구버전 내용 수정
- 공식 문서에 새로 생긴 주제의 신규 문서 추가
- 공식에서 제거·폐기된 주제의 문서 삭제
- 디렉터리 README.md 인덱스 생성/갱신 (모든 디렉터리에 인덱스를 두는 것이 이 저장소의 정책)
- 작업 유형별 한글 커밋 + push

## 왜 ultracode 워크플로를 쓰는가

전수조사는 수십 개의 공식 문서 페이지를 fetch해서 수십 개의 로컬 문서와 문장 단위로 대조하는 작업이다. 단일 컨텍스트로는 페이지 몇 개만 읽어도 컨텍스트가 가득 차고, 순차 처리하면 너무 오래 걸리며, 한 에이전트가 조사와 검증을 겸하면 자기 오류를 발견하지 못한다. 그래서 이 스킬의 무거운 단계(조사·대조·작성·검증)는 **반드시 Workflow 도구로 병렬 에이전트를 최대한 활용해** 실행한다. 사용자가 이 스킬을 호출한 것 자체가 멀티에이전트 오케스트레이션에 대한 명시적 opt-in이다. 인라인(메인 루프)에서 직접 하는 것은 가벼운 판단·매핑·삭제·커밋뿐이다.

워크플로는 한 덩어리로 만들지 말고 **단계별로 나눠 순차 실행**한다. 각 워크플로의 결과를 메인 루프가 읽고 판단한 뒤 다음 워크플로를 설계해야, 조사 결과에 맞춰 대조·작성 계획을 정확히 세울 수 있다. 구체적인 스크립트 골격과 스키마는 `references/workflow-patterns.md`를 읽고 상황(문서 수, 제품 규모)에 맞게 조정해서 쓴다.

## 품질 원칙 (모든 단계에 적용)

1. **추측 금지.** 문서에 들어가는 모든 사실(명령어, 파라미터, 엔드포인트, 가격, 제한값)은 에이전트가 WebFetch로 실제 가져온 공식 문서 내용에 근거해야 한다. 모델의 사전 지식으로 채우면 구버전 정보가 섞인다 — 이 저장소의 존재 이유가 "최신 공식 문서의 신뢰 가능한 정리본"이므로 이것이 무너지면 전부 무너진다.
2. **작성과 검증은 다른 에이전트가.** 작성한 에이전트는 자기 오류를 못 본다. 검증 에이전트는 "이 문서에서 틀린 부분을 찾아 반박하라"는 적대적 프레임으로 공식 문서와 재대조한다.
3. **출처를 문서에 남긴다.** 각 문서 상단에 원문 URL을 기록한다. 다음 동기화 때 이 링크가 대조 기준이 된다.
4. **불확실하면 빼거나 표시한다.** 공식 문서에서 확인되지 않는 내용은 싣지 않는다. beta/deprecated 표기는 공식 문서의 표기를 따른다.

## 0단계 — 입력 해석과 모드 판정 (인라인)

1. **대상 디렉터리 확정.** 사용자가 지정한 디렉터리(`@codex/`, `codex`, `openrouter/` 등)를 저장소 루트 기준으로 해석한다. 여러 개를 지정하면 디렉터리별로 이 스킬의 전체 파이프라인을 각각 수행한다(워크플로는 디렉터리 단위로 분리 — 커밋 단위가 섞이지 않게).
2. **제품 식별.**
   - 디렉터리에 기존 문서가 있으면: 각 문서 상단의 원문/참조 링크를 추출해 공식 문서 베이스 URL을 확정한다. 이것이 가장 신뢰할 수 있는 근거다.
   - 빈 디렉터리거나 존재하지 않으면: 디렉터리 이름으로 웹 검색해 제품을 식별한다. 이름이 모호하면(예: "codex"가 OpenAI Codex인지 다른 것인지 불분명) 추측으로 진행하지 말고 AskUserQuestion으로 확인한다 — 수십 개 에이전트를 엉뚱한 제품에 투입하는 것이 최악의 낭비다.
3. **모드 판정.**
   - 디렉터리에 `.md` 문서가 있음 → **업데이트 모드** (1 → 2 → 3 → 4 → 5단계)
   - 비어 있거나 신규 → **신규 작성 모드** (1 → 2 → 4 → 5단계, Audit 생략)
4. **오늘 날짜를 기록해 둔다.** Workflow 스크립트 안에서는 `Date`를 쓸 수 없으므로, 메인 루프가 오늘 날짜(YYYY-MM-DD)를 `args.today`로 모든 워크플로에 전달한다. README의 "최종 업데이트" 표기에 쓴다.

## 1단계 — Discovery 워크플로: 공식 문서 전수조사

목표: 그 제품의 공식 문서 **전체 지도**(페이지 URL + 제목 + 주제 + 중요도)를 만든다. 이 지도가 불완전하면 이후 모든 단계가 불완전해지므로, 한 가지 방법이 아니라 **여러 각도의 멀티모달 스윕**을 병렬로 돌린다:

- sitemap.xml / robots.txt / docs 인덱스 페이지 크롤링
- 공식 docs 사이트의 네비게이션(사이드바) 구조 추출
- 체인지로그 / 릴리스 노트 / 공식 블로그에서 최근 변경·신기능 수집
- GitHub 저장소 (README, docs/ 디렉터리, 위키, 주요 릴리스)
- API 레퍼런스 등 별도 호스팅된 보조 문서 허브

각 앵글은 서로 못 보는 페이지를 발견한다. 스윕 후 메인 루프가 URL 기준으로 dedup하고, **completeness critic** 에이전트 하나에게 "이 인벤토리에서 빠진 영역이 있는가?"를 묻는다. critic이 찾아낸 누락 영역은 추가 스윕으로 보강한다.

산출물: 페이지 인벤토리(JSON) + 최근 변경사항 목록. 워크플로 에이전트가 웹에 접근하려면 프롬프트에 "ToolSearch로 WebSearch/WebFetch를 로드해서 사용하라"를 반드시 포함한다(스크립트 템플릿에 이미 들어 있다).

## 2단계 — 매핑과 작업 계획 (인라인)

메인 루프가 인벤토리와 로컬 문서 목록을 놓고 **커버리지 매트릭스**를 만든다:

| 공식 문서 주제 | 로컬 문서 | 판정 후보 |
| --- | --- | --- |
| 인벤토리에 있고 로컬에도 있음 | `NN-xxx.md` | → 3단계 Audit 대상 |
| 인벤토리에 있는데 로컬에 없음 | — | → 신규 작성 후보 |
| 로컬에 있는데 인벤토리에 없음 | `NN-xxx.md` | → 삭제 후보 (단, Audit에서 한 번 더 확인) |

신규 작성 후보는 중요도(core > secondary > minor)로 우선순위를 매긴다. 사소한 페이지 하나하나를 전부 별도 문서로 만들 필요는 없다 — 기존 문서들의 주제 단위(설치, CLI 레퍼런스, 설정, 보안 등)와 비슷한 굵기로 묶는 것이 이 저장소의 스타일이다.

신규 작성 모드라면 여기서 인벤토리를 바탕으로 **문서 목차 설계**를 한다: `00-overview.md`부터 시작하는 10~16개 내외의 문서 구성. 기존 디렉터리들(`claude-code/`, `codex/`, `openrouter/`)의 구성이 좋은 본보기다.

## 3단계 — Audit 워크플로: 문서별 병렬 대조 (업데이트 모드만)

로컬 문서 하나당 에이전트 하나를 붙여 **전부 병렬로** 대조한다. 각 에이전트는:

1. 담당 로컬 문서를 Read로 정독
2. 매핑된 공식 문서 페이지들을 WebFetch로 가져옴
3. 문장 단위 대조 → 구조화된 판정 반환:
   - `keep` — 최신 상태, 손댈 필요 없음
   - `update` — 수정 필요. 구체적으로 무엇이 어떻게 다른지 항목별 목록 (이 목록이 4단계 작성 에이전트의 작업 지시서가 된다)
   - `delete` — 주제 자체가 공식에서 제거/폐기됨. 근거 URL 필수

삭제 후보(2단계에서 인벤토리에 없던 문서)는 여기서 반드시 재확인한다 — Discovery가 놓쳤을 뿐 공식 문서가 존재할 수 있다. 담당 에이전트에게 "이 주제가 정말 공식에서 사라졌는지 직접 검색·확인하라"고 지시한다.

Audit이 끝나면 메인 루프가 최종 작업 목록을 확정하고 사용자에게 한 줄 요약을 보고한다: "수정 N건, 신규 M건, 삭제 K건, 유지 J건". 보고만 하고 멈추지 말고 바로 4단계로 진행한다(삭제가 5건 이상으로 많을 때만 목록을 보여주고 AskUserQuestion으로 확인 — 대량 삭제는 Discovery 실패의 신호일 수 있다).

## 4단계 — Write & Verify 워크플로: 병렬 작성 + 적대적 검증

작업 항목(수정 N건 + 신규 M건)을 하나의 pipeline에 넣는다. 항목별로 `작성 → 검증 → (실패 시) 수정`이 독립적으로 흐르므로 배리어 없이 최대 병렬이 유지된다:

1. **Write**: 항목당 에이전트 하나가 공식 문서 페이지들을 WebFetch한 뒤 문서를 직접 Write/Edit한다. 작성 결과(파일 경로, 다룬 주제, 사용한 출처 URL)를 구조화해 반환한다. 문서 내용을 메인 루프로 반환하지 않는다 — 컨텍스트가 터진다.
   - 각 에이전트는 서로 다른 파일을 담당하므로 worktree 격리는 불필요하다.
   - 컨벤션(`references/conventions.md`)의 핵심 규칙을 작성 프롬프트에 요약해 넣는다. 특히: 한국어, 파일명 규칙, 문서 헤더의 원문 링크, 표 중심 정리.
2. **Verify**: 다른 에이전트가 방금 쓰인 파일을 Read하고 같은 공식 문서와 재대조한다. 프레임은 적대적으로 — "틀린 사실, 누락된 핵심, 출처 없는 주장을 찾아 반박하라". 통과/실패 + 문제 목록을 반환.
3. **Fix**: 실패 항목만 세 번째 에이전트가 문제 목록을 받아 수정한다. 1회 수정 후에도 남는 문제는 메인 루프가 모아서 직접 처리하거나 사용자에게 보고한다(무한 루프 방지).

번호 체계: 기존 문서의 번호는 유지한다(커밋 이력·외부 링크 안정성). 신규 문서는 기존 마지막 번호 뒤에 추가한다. 주제상 중간에 들어가야 자연스러워도 번호를 전부 밀지 않는다 — README 인덱스가 카테고리별로 묶어주므로 번호 순서가 주제 순서일 필요는 없다. 전면 재배열은 신규 작성 모드에서만 한다.

## 5단계 — 마무리: 삭제, 인덱스, 커밋 (인라인)

1. **삭제 실행.** Audit에서 `delete` 판정된 파일을 메인 루프가 직접 삭제한다(에이전트에게 삭제를 위임하지 않는다 — 파괴적 작업은 중앙에서 통제).
2. **README.md 인덱스 생성/갱신.** `references/conventions.md`의 인덱스 템플릿을 따른다. 카테고리별 문서 표 + 빠른 참조 + 원문 링크 + "최종 업데이트: YYYY-MM-DD". 4단계 결과(각 문서의 주제 요약)를 재료로 쓰면 다시 읽을 필요가 없다.
3. **커밋 + push.** 작업 유형별로 논리 단위를 나눠 커밋한다. 한글 커밋 메시지, git convention prefix. 이 저장소의 실제 커밋 스타일:
   - `docs: <제품> 공식 문서 전수조사 - 신규 문서 N개 추가`
   - `fix: 기존 <제품> 문서 N개 수정 - 공식 문서 대조 결과 반영`
   - `docs: <제품> 폐기 문서 N개 삭제 - 공식 문서에서 제거된 기능`
   - `docs: README 인덱스 업데이트 - 신규 문서 및 섹션 반영`
4. **최종 보고.** 수정/신규/삭제/유지 건수, 주요 변경 내용 요약(예: "신기능 X 문서 추가, Y 파라미터 폐기 반영"), 커밋 해시.

## 참조 파일

- `references/conventions.md` — 이 저장소의 문서 작성 컨벤션 전체(파일명, 문서 구조, README 인덱스 템플릿, 커밋 규칙). **2단계 계획 수립 전과 4단계 작성 프롬프트 구성 전에 반드시 읽는다.**
- `references/workflow-patterns.md` — 1·3·4단계 Workflow 스크립트 골격과 출력 스키마, Workflow 도구의 제약사항(meta 리터럴, Date 금지 등). **각 워크플로 호출 직전에 해당 템플릿을 읽고 상황에 맞게 조정한다.**
