# 모범 사례

> Codex를 효과적으로 사용하기 위한 핵심 습관과 검증된 실무 가이드입니다.

**참조**: <https://developers.openai.com/codex/learn/best-practices>, <https://developers.openai.com/codex/agents-md>, <https://developers.openai.com/codex/skills>

## 강력한 첫 사용: 컨텍스트 및 프롬프트

명확한 프롬프트는 더 안정적인 결과를 보장합니다. 프롬프트에 다음 네 가지를 포함하세요.

| 요소 | 설명 | 예시 |
| --- | --- | --- |
| **목표 (Goal)** | 무엇을 변경하거나 만들 것인가 | "사용자 인증 모듈 리팩토링" |
| **컨텍스트 (Context)** | 어떤 파일, 폴더, 에러가 관련있는가 | "@auth.ts, @auth.test.ts 참조" |
| **제약사항 (Constraints)** | 어떤 표준, 아키텍처, 규칙을 따를 것인가 | "Express 미들웨어 패턴 사용" |
| **완료 조건 (Done when)** | 작업 완료의 기준 | "모든 테스트 통과, 린트 에러 없음" |

> `@`를 사용하여 파일을 직접 참조할 수 있습니다. Codex App에서는 음성 받아dictation을 활용해 빠르게 프롬프트를 작성할 수도 있습니다.

## 추론 수준 선택

작업 복잡도에 따라 적절한 추론 수준을 선택하세요.

| 수준 | 적합한 작업 | 특징 |
| --- | --- | --- |
| **Low** | 빠르고 잘 정의된 작업 | 속도 우선 |
| **Medium** | 일반적인 복잡도의 변경 | 균형잡힌 추론 |
| **High** | 복잡한 변경, 디버깅 | 심층 분석 |
| **Extra High** | 긴 에이전트적 작업, 심층 추론 필요 | 최대 추론 |

## 복잡한 작업은 먼저 계획

복잡하거나 모호한 작업은 코드 작성 전에 계획을 세우는 것이 효과적입니다.

### Plan 모드

- **활성화**: `/plan` 명령어 또는 `Shift`+`Tab`
- Codex가 컨텍스트를 수집하고, 명확화 질문을 하며, 구현 전 계획을 수립합니다.

### 인터뷰 요청

아이디어는 있지만 명확히 설명하기 어려운 경우, Codex에게 질문하도록 요청하세요.

```
먼저 나에게 질문해서 요구사항을 명확히 한 다음 코드를 작성해줘
```

### PLANS.md 템플릿

고급 워크플로우에서는 `PLANS.md` 또는 실행 계획 템플릿을 구성하여 장기 실행 또는 다단계 작업에 활용할 수 있습니다.

## AGENTS.md 활용

`AGENTS.md`는 에이전트를 위한 README로, 자동으로 컨텍스트에 로드됩니다.

### 포함할 내용

- 리포지토리 레이아웃 및 중요 디렉토리
- 프로젝트 실행 방법
- 빌드, 테스트, 린트 명령어
- 엔지니어링 규칙 및 PR 기대사항
- 제약사항 및 금지 규칙
- "완료"의 정의 및 검증 방법

### 계층 구조

| 레벨 | 위치 | 용도 |
| --- | --- | --- |
| 글로벌 | `~/.codex/AGENTS.md` | 개인 기본 설정 |
| 리포지토리 | 프로젝트 루트 `AGENTS.md` | 팀 공유 표준 |
| 하위 디렉토리 | 디렉토리별 `AGENTS.md` | 로컬 규칙 (더 구체적인 것이 우선) |

> 각 디렉토리에서 Codex는 먼저 `AGENTS.override.md`를 찾고, 있으면 사용하며, 없으면 `AGENTS.md`를 사용합니다.

### 초기 생성

```bash
/init    # 현재 디렉토리에 AGENTS.md 스캐폴드 생성
```

> `/init`으로 생성된 파일은 팀의 실제 워크플로우에 맞게 수정해야 합니다.

### 유지 관리 팁

- 짧고 정확한 `AGENTS.md`가 길고 모호한 파일보다 유용합니다
- Codex가 같은 실수를 반복하면 회고를 요청하고 `AGENTS.md`를 업데이트하세요
- 파일이 너무 커지면 메인 파일은 간결하게 유지하고 작업별 마크다운 파일을 참조하세요

## 구성 관리

Codex의 동작을 세션과 서피스 전반에서 일관되게 만드는 핵심 방법입니다.

| 위치 | 용도 | 범위 |
| --- | --- | --- |
| `~/.codex/config.toml` | 개인 기본 설정 | 글로벌 |
| `.codex/config.toml` | 프로젝트별 설정 | 프로젝트 |
| CLI 오버라이드 (`--config`, `-c`) | 일회성 설정 변경 | 세션 |
| `$CODEX_HOME/profile-name.config.toml` | 프로필별 오버라이드 | 프로필 |

```toml
# ~/.codex/config.toml 예시
model = "gpt-5.5"
approval_policy = "on-request"
sandbox_mode = "workspace-write"

[sandbox_workspace_write]
network_access = false
```

## 검증 루프

Codex에게 단순히 코드를 생성하는 것에 그치지 말고, **테스트, 검증, 리뷰**까지 요청하세요.

### 검증 단계

1. 변경사항에 대한 테스트 작성/업데이트
2. 관련 테스트 스위트 실행
3. 린트, 포맷팅, 타입 체크 확인
4. 최종 동작이 요청사항과 일치하는지 확인
5. diff를 버그, 회귀, 위험 패턴에 대해 리뷰

### /review 명령어

```bash
/review              # 베이스 브랜치 대비 PR 스타일 리뷰
/review uncommitted  # 커밋되지 않은 변경 리뷰
/review commit       # 특정 커밋 리뷰
```

> `AGENTS.md`에서 `code_review.md`를 참조하면 팀의 리뷰 가이드라인을 리뷰 시 자동 적용할 수 있습니다.

## MCP 사용 시기

MCP (Model Context Protocol)는 Codex를 외부 도구 및 시스템에 연결하는 개방형 표준입니다.

### MCP가 적합한 경우

| 상황 | 이유 |
| --- | --- |
| 필요한 컨텍스트가 리포지토리 밖에 있을 때 | 외부 데이터 접근 |
| 데이터가 자주 변경될 때 | 실시간 정보 |
| 도구 사용이 반복적인 지시보다 나을 때 | 자동화 |
| 사용자/프로젝트 간 재사용 가능한 통합이 필요할 때 | 표준화 |

### MCP 서버 설정

```toml
[mcp_servers.docs]
command = "docs-server"
default_tools_approval_mode = "approve"
```

```bash
# CLI에서 MCP 서버 추가
codex mcp add <name> --url <url>
```

> 실제 워크플로우를 개선하는 도구만 추가하세요. 모든 도구를 연결하는 것으로 시작하지 마세요.

## Skills 활용

반복 워크플로우를 Skill로 패키지화하면 긴 프롬프트나 반복적인 대화 없이 일관된 결과를 얻을 수 있습니다.

### Skill 작성 원칙

- 각 스킬은 **하나의 작업**에만 집중
- 2~3개의 구체적인 사용 사례로 시작
- 명확한 입력/출력 정의
- 설명에는 스킬이 **무엇을 하는지**와 **언제 사용하는지** 포함
- 실제 사용자가 말할 법한 트리거 문구 포함

### 스킬 위치

| 유형 | 경로 |
| --- | --- |
| 개인 스킬 | `$HOME/.agents/skills/` |
| 팀 공유 스킬 | 리포지토리 내 `.agents/skills/` |

### 스킬 생성

`$skill-creator` 스킬을 사용하여 첫 버전을 스캐폴드합니다. 로컬에서 반복한 후 준비되면 플러그인으로 패키지화합니다.

> 같은 프롬프트를 반복 사용하거나 같은 워크플로우를 반복 수정하고 있다면, 그것은 스킬이 되어야 합니다.

## Automations

안정적인 워크플로우는 자동화하여 백그라운드에서 예약 실행할 수 있습니다.

### 개념

| 개념 | 역할 |
| --- | --- |
| **Skill** | 실행 방법 (method) |
| **Automation** | 실행 일정 (schedule) |

### 설정

Codex App의 **Automations** 탭에서 프로젝트, 프롬프트(스킬 호출 가능), 실행 주기, 실행 환경을 선택합니다.

### 적합한 자동화 대상

- 최근 커밋 요약
- 가능한 버그 스캔
- 릴리스 노트 초안 작성
- CI 실패 확인
- 스탠드업 요약
- 반복 가능한 분석 워크플로우

> 워크플로우가 아직 안정적이지 않다면 먼저 스킬로 만들어 개선한 후 자동화하세요.

## 세션 관리

Codex 세션은 단순한 채팅 기록이 아니라 시간이 지남에 따라 컨텍스트, 결정, 작업을 축적하는 작업 스레드입니다.

### 유용한 명령어

| 명령어 | 용도 |
| --- | --- |
| `/resume` | 저장된 대화 재개 |
| `/fork` | 원래 대화를 보존하면서 새 스레드 생성 |
| `/compact` | 긴 스레드의 이전 컨텍스트 요약 (자동 compact도 수행됨) |
| `/agent` | 병렬 에이전트 실행 시 활성 에이전트 스레드 전환 |
| `/status` | 현재 세션 상태 확인 |
| `/experimental` | 실험적 기능 토글 |
| `/theme` | 구문 강조 테마 선택 |
| `/apps` | ChatGPT 앱 직접 사용 |
| `/permissions` | 권한 설정 변경 |

### 세션 재개 (CLI)

```bash
# 세션 선택 UI 표시
codex resume

# 가장 최근 세션 재개
codex resume --last

# 특정 세션 ID로 재개
codex resume 7f9f9a2e-1b3c-4c7a-9b0e-123456789abc

# 모든 세션 표시 (CWD 필터링 비활성화)
codex resume --all
```

### 세션 관리 원칙

- **하나의 작업 단위 = 하나의 스레드**: 같은 문제에 대한 작업은 같은 스레드에서 진행
- **포크는 진정한 분기 시에만**: 작업이 본질적으로 나뉠 때만 포크
- **서브에이전트 활용**: 탐색, 테스트, 분류 등은 서브에이전트에 위임

## 피해야 할 일반적인 실수

| 실수 | 올바른 접근 |
| --- | --- |
| 내구성 있는 규칙을 프롬프트에 반복 입력 | `AGENTS.md`나 스킬로 이동 |
| 빌드/테스트 명령어 실행 방법을 알려주지 않음 | `AGENTS.md`에 명령어 명시 |
| 복잡한 작업에서 계획 단계 건너뜀 | Plan 모드 또는 인터뷰 먼저 수행 |
| 워크플로우를 이해하기 전에 전체 권한 부여 | 기본 타이트, 필요시 완화 |
| git worktree 없이 같은 파일에서 여러 스레드 실행 | worktree 사용 |
| 안정적이지 않은 작업을 바로 자동화 | 먼저 수동으로 안정화 후 자동화 |
| 단계별로 지켜보려고 함 | 병렬로 작업하며 활용 |
| 프로젝트당 하나의 스레드 사용 | 작업당 하나의 스레드 사용 |

## 트러블슈팅

### 사이드 패널 파일

Codex App의 사이드 패널에서 파일을 직접 열어 변경사항을 검토하고 특정 행을 클릭하여 피드백을 제공할 수 있습니다.

### 보관된 스레드

긴 스레드는 자동으로 compact됩니다. `/compact` 명령어로 수동 compact도 가능합니다.

### 워크트리

```bash
# 여러 작업을 병렬로 수행할 때
codex --cd apps/frontend --add-dir ../backend --add-dir ../shared
```

### 로그 위치

| 항목 | 경로 |
| --- | --- |
| 세션 기록 | `~/.codex/sessions/` |
| 로그 파일 | `$CODEX_HOME/log/` (또는 `log_dir` 설정) |
| TUI 로그 | `log_dir` 설정 시 `codex-tui.log` 생성 |
